1.  Introduction 
This document is the complete technical specification for every Host-to-Host (H2H) service PayBill offers. It is 
written for the institution's own developers: it specifies exactly what to call, what to send, and what to expect back, 
for each service your institution has been onboarded onto. 
HOW TO READ THIS DOCUMENT: 
Each endpoint is presented as: a coloured method-and-path banner, the headers it requires, an example request 
payload where applicable, and then every response type, clearly labelled SUCCESS or ERROR alongside its HTTP status 
code. For each service, a dedicated “Your Webhook” section explains exactly what you need to build to receive ZICB's 
own notifications back. 
 
1.1  The Five Services 
Service What it does 
Auth Issues and verifies the access token every other call depends on. 
NFS B2W Pay many individual mobile money wallets and bank accoiunts at once, in a single batch. 
Internal Fund Transfer Move money directly between accounts that both already sit inside ZICB. 
RTGS Send large or time-critical payments to other banks, settled individually and immediately. 
DDACC Another channel for sending payments to other banks, alongside RTGS. 
 
1.2  Services & Base URLs 
Each service is served from its own address. All are reachable over HTTPS; the specific host and port differ between 
the SIT, DEV, UAT, and Production environments and will be confirmed by ZICB IT as part of onboarding. 
Service Base URL 
Auth https://IP/DOMAIN:PORT 
NFS B2W https://IP/DOMAIN:PORT 
Internal Fund Transfer https://IP/DOMAIN:PORT 
RTGS https://IP/DOMAIN:PORT 
DDACC https://IP/DOMAIN:PORT

directly as a starting point for your own integration testing.

2.  Authentication 
Every business call into any PayBill H2H service is authorised by a Bearer access token, obtained by exchanging your 
institution's client credentials. The same token authorises calls to every service your institution is allowed to use — 
you do not need a separate token per service. 
Credential Used for Carried as 
client_id / client_secret Exchanged for an access token, which authorises every 
business call 
JSON body, then Bearer 
token 
 
KEEP YOUR CREDENTIALS SAFE: 
Your client_id and client_secret authorise every call your institution makes, across every service. Keep both 
confidential and never expose them outside your own backend — treat them exactly as you would a 
password. 
 
2.1  Get Access Token 
Exchanges your institution's client credentials for a short-lived Bearer access token. Call this first, and again 
whenever your token expires. 
POST /h2h/auth/grant-type/client-credentials 
Base URL (Auth): https://IP/DOMAIN:PORT  — replace with the actual host and port for your environment 
Headers 
Header Value 
Content-Type application/json 
 
Request & Response 
  REQUEST PAYLOAD  
Example request body 
{ 
  "client_id": "<YOUR_CLIENT_ID>", 
  "client_secret": "<YOUR_CLIENT_SECRET>", 
  "grant_type": "client_credentials" 
} 
 
  RESPONSE  ·  SUCCESS  ·  200 OK  
Example response body 
{ 
  "access_token": "<ACCESS_TOKEN>", 
  "expires_in": 5400, 
  "token_type": "Bearer" 
}

Field Type Required Description

TOKEN LIFETIME: 
The access token returned is valid for the number of seconds given in expires_in (5,400 seconds — 90 
minutes). Request a new token before it expires; don't wait for a call to fail.

2.2  Verify Access Token 
Lets you confirm whether a token you're holding is still valid, and see exactly when it was issued and when it 
expires, without needing to make a real business call first. 
GET /h2h/auth/grant-type/client-credentials/verify-token 
Base URL (Auth): https://IP/DOMAIN:PORT  — replace with the actual host and port for your environment 
Headers 
Header Value 
Authorization Bearer <ACCESS_TOKEN> 
 
This is a GET request — there is no request payload; the token being checked is carried entirely in the Authorization 
header. 
Responses 
  RESPONSE  ·  SUCCESS  ·  200 OK  
Example response body 
{ 
  "sub": "4176d097-c677-497c-aaf5-3fe08e051eb2", 
  "valid": true, 
  "payload": { 
    "exp": 1785322931, 
    "iat": 1785317531, 
    "sub": "4176d097-c677-497c-aaf5-3fe08e051eb2" 
  }, 
  "expires_at": 1785322931, 
  "issued_at": 1785317531 
} 
 
  RESPONSE  ·  ERROR  ·  401 Unauthorized  
The token's expiry time has passed. 
{ 
  "error": "invalid_token", 
  "valid": false, 
  "error_description": "Token has expired" 
} 
 
  RESPONSE  ·  ERROR  ·  401 Unauthorized  
The token's signature doesn't match — it may be malformed, altered, or issued by a different environment. 
{ 
  "error": "invalid_token", 
  "valid": false, 
  "error_description": "Signature verification failed" 
}

  NFS B2W — Bank to Wallet 
NFS B2W lets your institution pay many individual mobile money wallets at once, in a single batch — used, for 
example, to pay a large number of people directly into their mobile money accounts.

3.2  Send Money (Bulk Payout) 
Submits a batch of one or more payouts to be disbursed to individual mobile wallets. A batch is accepted 
immediately; the actual disbursement of each item happens shortly afterwards, and can be followed up using 
Transaction Status (Section 3.4) or your own webhook (Section 3.5). 
POST /h2h/nfs/b2w/send-money 
Base URL (NFS B2W): https://IP/DOMAIN:PORT  — replace with the actual host and port for your environment 
Headers 
Header Value 
Content-Type application/json 
Authorization Bearer <ACCESS_TOKEN> 
Standard Request Payload 
Field Type Required Description 
reference string Mandatory A unique reference for this whole batch, chosen by you. Used 
to detect and safely reject accidental duplicate submissions. 
count integer Mandatory The number of transactions included in this batch. 
region_code string Mandatory The region/revenue/purpose code the paying branch belongs 
to. 
total_amount decimal Mandatory The sum of every transaction amount in the batch — must 
match the sum of the individual items. 
transactions array Mandatory The list of individual payouts making up this batch. 
Each entry inside transactions: 
Field Type Required Description 
prcn_number string Mandatory Your own unique reference for this individual payment 
(Payment Requisition Confirmation Note number). 
account_number string Mandatory The beneficiary's wallet number. 
institution_id string Mandatory The code identifying the receiving mobile money network (see 
Section 3.3). 
amount decimal Mandatory The amount to pay this beneficiary. 
is_retry 0 or 1 Mandatory Set to 1 if this item is a resubmission of a previously failed 
payment; otherwise 0. 
retry_count integer Mandatory How many times this specific item has already been retried. 
ZICB allows a maximum of 10 retries per prcn_number. 
number_of_bags integer Optional A descriptive field used by some institutions; ignored if not 
relevant to your use case. 
  REQUEST PAYLOAD  
Example request body

3.3  Participants 
Returns the list of NFS B2W participants we currently support, along with the exact institution_id code to use for 
each one in Name Lookup and Send Money, and the pattern their account numbers should match. 
GET /h2h/nfs/b2w/participants 
Base URL (NFS B2W): https://IP/DOMAIN:PORT  — replace with the actual host and port for your environment 
Headers 
Header Value 
Authorization Bearer <ACCESS_TOKEN> 
This is a GET request — there is no request payload. 
Responses 
  RESPONSE  ·  SUCCESS  ·  200 OK  
A shortened sample — call the live endpoint for the complete, current list. 
{

10.  Glossary 
Term Meaning 
H2H Host-to-Host — a direct, system-to-system integration between your institution and ZICB. 
NFS The National Financial Switch — the interbank / mobile-money network NFS B2W payouts 
are routed through. 
B2W Bank to Wallet — paying funds from a bank account directly into a mobile money wallet. 
RTGS Real-Time Gross Settlement — payments to other banks, settled individually and 
immediately. 
DDACC A second channel, alongside RTGS, for sending payments to other banks. 
Batch A group of one or more payments submitted together in a single Send Money call. 
Item A single payment within a batch — one beneficiary, one amount. 
prcn_number Your own unique reference for one specific item, used for reconciliation and duplicate 
detection. 
participant_id / 
institution_id 
The code identifying which mobile money network a beneficiary's wallet belongs to (NFS 
B2W). 
branch_code The ZICB branch code an account is held at (Internal FT). 
receiver_sort_code / 
receiver_bic 
The codes identifying the receiving bank and branch for a payment to another bank (RTGS 
/ DDACC). 
region_code The region/revenue/purpose code associated with the paying branch or account. 
CIF Customer Information File number — the unique ID ZICB uses to identify an account 
holder. 
Bearer token A short-lived access token that authorises your calls, obtained via Section 2.1. 
Webhook An HTTP address on your own system that ZICB calls to notify you of an outcome, without 
you having to ask first.
